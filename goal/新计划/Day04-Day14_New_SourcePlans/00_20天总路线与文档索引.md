# Pi-style Agent Harness：20 天从单 Agent 到生产级 Multi-Agent

> 项目目标：先用 Python 从零做出一个**看得懂、能解释、能调试**的 Single Agent Harness，再在不推倒 V1 核心能力的前提下，用 LangGraph 升级为 `Main Agent + Coding SubAgent + Research/Review SubAgent` 的 Multi-Agent 系统。

---

## 0. 这 20 天到底在学什么

这不是“调用一个 `create_agent()` 跑起来”的项目。

核心路线是：

```text
Model
  ↓
Function Calling
  ↓
手写 Agent Loop
  ↓
Tool Contract / Registry / Executor
  ↓
Docker Sandbox
  ↓
Agentic RAG
  ↓
Session / Checkpoint / Recovery
  ↓
Context Manager / Compaction
  ↓
Streaming / Event
  ↓
MCP / Skills
  ↓
LangGraph
  ↓
Multi-Agent
  ↓
CRAG / Web Research
  ↓
Observability / Evaluation
```

最终你应该能回答：

- LLM 返回 `tool_calls` 后，Agent Runtime 到底做了什么？
- `tool_call_id` 为什么必须和 `ToolMessage` 一一配对？
- 为什么工具重试只能有一个统一 Retry Layer？
- 为什么 Checkpoint 不能代替 Tool Operation Ledger？
- 为什么完整 Session History 不能直接等于 Runtime Context？
- RAG 为什么可以作为 Tool，而不是固定 Pipeline？
- Multi-Agent 为什么适合用 LangGraph，而 V1 不需要？
- Agent 中断时，如果工具已经执行但 `tool_result` 没写成功，怎么恢复？
- 为什么原始工具输出必须持久化，但不应该全部塞回模型 Context？

# 1. 冻结技术栈

## Runtime

- Windows 11
- Docker Desktop
- Python 3.11
- `uv`
- `pytest`
- `ruff`
- `pydantic`
- `aiosqlite`

## LLM

LangChain 只负责：

- ChatModel Provider 兼容
- `HumanMessage / AIMessage / ToolMessage`
- `bind_tools()`
- `AIMessage.tool_calls`

禁止拿它替代：

- Agent Loop
- ToolRegistry
- ToolExecutor
- Retry
- ToolResult
- Checkpoint
- ContextManager

## ModelProvider

第一阶段支持：

- Qwen
- DeepSeek
- OpenAI-compatible

原则：

```text
ModelProvider 只负责创建模型
Agent Runtime 不关心具体 Provider
```

V1 不做自动 Fallback，V2 再加入。

## RAG

```text
Markdown
  ↓
自研 Heading-aware Parser
  ↓
Token-aware Chunker
  ↓
512 token / overlap 65 token
  ↓
SiliconFlow BGE-M3
  ↓
Milvus Standalone
```

## 本地状态

SQLite：

- sessions
- messages
- checkpoints
- tool_operations
- knowledge_documents

外部 Artifact Store：

- 完整 Bash 输出
- 超长日志
- 大型 Tool Result
- 需要后续按需取回的原始数据

# 1.1 API/版本安全规则

这套手册冻结的是**架构和学习顺序**，不是把第三方 SDK 的某个旧版本调用写死。开发到 LangChain、LangGraph、MCP、Milvus、Langfuse、EvalScope、联网搜索 Provider 时：

1. 先看该组件当前官方文档；
2. 只调整 Adapter 层的 import/参数；
3. 不因为 SDK API 变化改变本项目的 Agent Loop / Tool Contract / Checkpoint 核心；
4. Claude Code 若提出使用 `create_agent()` 等黑盒来“省事”，按本项目约束拒绝。

9. 日志必须包含足以定位故障的 run_id/session_id/tool_call_id 等上下文字段。
10. 不要隐藏核心执行流。

# 7. Codex 的总 Review Prompt

```text
请作为独立 Reviewer 审查当前 checkpoint。

重点不是帮我“重构得更高级”，而是判断当前实现是否正确、透明、可学习。

必须检查：
1. 是否偷用了 create_agent / AgentExecutor / 现成 Agent Runtime。
2. Agent Loop 是否仍然一眼能看懂。
3. Tool Call 与 Tool Result 是否通过 tool_call_id 严格配对。
4. Tool 参数是否在执行前经过 Pydantic 校验。
5. Retry 是否只存在 ToolExecutor 一个层级，是否有 Retry Amplification 风险。
6. 参数错误、暂时性错误、确定性错误是否分类正确。
7. READ_ONLY 并发是否可能与 MUTATING Tool 产生竞态。
8. Checkpoint 是否存在“状态保存了但副作用没对账”的恢复漏洞。
9. Context 压缩是否会破坏原始 Session History。
10. 测试是否真正验证行为，而不是只追求覆盖率。
11. 是否过度封装、过早抽象、文件拆得太碎。
12. 安全、异常处理、资源释放、异步代码是否有明显问题。

输出：
- P0：必须修
- P1：建议本 checkpoint 修
- P2：以后再优化
- 明确指出哪些地方不要改，避免过度设计。
```
