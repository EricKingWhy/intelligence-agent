# 集成提示词：#181 窄屏触摸 ⋯ 菜单可达（前端）

> 给集成 AI（`D:\intelligence-agent` 的 `main`）。本票**只动前端**，后端无对应改动，
> 因此没有跨端顺序约束——但仍建议与 #193/#191 那批一起走 §14.9 的"一次一条分支"。

## 1. 它解决什么

`@media (max-width: 820px)` 的 56px 图标轨里，会话行 / 项目行共用一个 24px 槽位：默认
显示「会话点 / 文件夹图标」，`hover` 或 `:focus-within` 时让位给 ⋯ 菜单。触摸设备上
这两条伪类都不可靠（没有 hover；iOS Safari 点 `button` 不进 `:focus-within`）⇒
FE-R11-09（会话级）与 #179（项目级）担保的操作在手机上可能**永远不显形**。

修复 = issue 推荐的方案 1（纯 CSS）：在 `@media (max-width: 820px) and (hover: none)`
下 ⋯ 常显，装饰性的点 / 文件夹图标退到背景。**没有 JS 改动、没有新交互**。

## 2. 合并与验收

```bash
# 后端 worktree 无本票改动；前端：
git -C D:/intelligence-agent-frontend log --oneline -2      # 找到 fix(e2e#181) 那条
# 在 main 上按 §13.3 合并后再验证
```

验收（浏览器，DevTools 设备模拟 → 打开触摸 + 800×900）：

1. 会话行与项目行都**不需要悬停**就能看到 ⋯，点开菜单项完整（会话：上移/下移/移出项目/
   删除会话…；项目：在此项目中新建任务/重命名项目/删除项目…）。
2. 鼠标（`(hover: hover)`）在同样宽度下**行为不变**：默认显示点 / 图标，悬停才换成 ⋯。
3. 宽屏（>820px）完全不变。
4. 两个状态信号仍在（槽位让给了 ⋯，信号改挂在 ⋯ 的颜色上）：有 run 在跑的会话行 ⋯ 是
   绿色（`--success`）；目录不存在的项目行 ⋯ 是黄色（`--warning`）。

## 3. 必须传下去的三条口径（别当成"等价替换"）

1. **触摸档的身份信息确实变弱了**：两层只剩同一个 ⋯ 芯片，比"点 vs 文件夹"更难一眼分辨
   "这是会话还是项目"。issue 收尾要求确认的正是这一点，本票按推荐方案 1 落地并**如实记在
   CSS 注释里**；若验收方认为不可接受，改法是槽位模型（行不再收缩成内容宽 29px，或 ⋯ 移到
   角落），属另一票——issue 明确要求这类改动"一次性定案"，不在可达性票里顺手做。
2. **只借颜色、不复用 `breathe`**：呼吸动画会把槽里唯一的入口周期性淡到 .55，与"提升
   可发现性"互相抵消。所以触摸档的"在跑"只剩颜色（弱于原来的实心绿点），这是取舍不是等价。
3. **窄屏"点行中央 = 打开菜单"是既成事实，不是本票引入的**。实测（800px）：行只有 29px 宽
   （内容宽，居中在 56px 轨里），⋯ 芯片 20px 压在中央，行相对 x∈[4,24) 命中的是 ⋯——而且
   它在 `opacity: 0` 时**照样接收指针事件**（`elementFromPoint` 验证过）。也就是说修复前
   触摸用户点行中央会打开一个**看不见**的菜单，本票只是把它变成看得见的入口。

## 4. 残余风险（本票未覆盖，建议另开票）

1. **宽屏触摸设备**（平板横屏 ≥820px、触摸笔记本）：⋯ 同样只在 `hover` / `:focus-within`
   下显形。AC1 字面指定 `(max-width: 820px) and (hover: none)`，所以本票**没动**宽屏；
   但同一类设备在宽屏档仍可能点不出菜单。判据与改法同上（放宽 `(hover: none)` 的宽度条件）。
2. **主指针是鼠标 + 有触摸屏的笔记本**：`(hover: none)` 不匹配（媒体查询看主指针），
   这类设备的触摸路径本票覆盖不到——Playwright 的 `hasTouch` 只模拟纯触摸档。
3. **窄屏行太窄**（29px）导致"点行选会话"几乎不可用（见 §3.3）：与 #181 同源但属槽位模型，
   建议与 §3.1 一起定案。
