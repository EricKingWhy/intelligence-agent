## 1. Ticket 与实施

### 1.1 开始一个 Ticket

1. 读取当前 Issue / Ticket 的验收条件、相关 Engineering Specification 和 Reuse Matrix；核对代码、测试、分支与工作树。
2. 把目标写成可验证结果并锁定范围。发现验收条件实质冲突、新证据证明目标不可实现或需要改变架构时，先报告证据与最小替代方案，再请求用户决定；未经批准不改 Issue、Ticket 或冻结规格。
3. 选择当前环境实际可用的工具和 Skills。`/implement`、`/ask-matt` 等未枚举的命令不是强制步骤，也不得假设存在。

### 1.2 实施与验证

1. 按最小垂直切片实现；修 Bug 或新增行为时先建立能命中真实症状的测试，再修复并复跑。
2. 每个 Ticket 跑与改动相称的 focused tests、lint / type check 和必要的集成测试；**不要求每张票都重跑全量测试**。高风险跨模块改动可在自然边界提前跑更广门禁。**全量的跑法见 §8.1（冻结树单次全量）——只跑一次，但必须跑在冻结树、且读数可机械传递。** 本步（TDD / 写测试 / 留测试）的**方法归属见 §9**——TDD 与测试质量用 **Matt（mattpocock）主开发 skills**（`tdd`），pstack 辅助项才按路径读 `docs/agents/skills/`；**不要在本文件重写一遍等价文字**。
3. 相关验证通过后再提交，commit message 描述实际工程事实；更新 `docs/SDD_TICKET_TRACKER.md` 的状态、提交、门禁证据和残余问题。`uv run` 后检查 `uv.lock`，处理规则见 §7 第 6 条（该条同时写明本仓当前的跑法：按用户指令用 `.venv` 里的 pytest，不用 `uv run`）。

## 2. 按风险安排 Code Review

V3-lite **不设固定 Ticket 数量或日历节奏**。在变更风险高、边界清楚且 review 能显著降低风险时审查；具体时点由实现证据决定。

以下改动默认值得独立 review：

- 凭证、权限、Sandbox / Host 边界或外部副作用；
- 删除、迁移、持久化、SessionEvent、Checkpoint、Recovery 或 Operation Ledger；
- 并发、取消、流式生命周期、共享进程状态；
- 公共 API / Contract、Provider 边界、跨模块或大范围改动；
- 测试结果与票面 / 规格不一致，或新证据改变原假设。

低风险文档、纯测试和局部机械改动可合并到最近的自然 review 边界。review 按项目需要覆盖 Standards 与 Correctness / Spec；审查范围必须准确记录实际读过的 base..tip。发现的问题按影响修复：疑难、间歇或并发 Bug 使用 `diagnosing-bugs` 建立可复现反馈环；其余做最小修复并跑对应测试。

**审查怎么派、给多大预算、取不到结论怎么办：见 §8.2–§8.3**（预算、只读纪律、结论行的强制要求，以及"修后重审"在基础设施故障下的有界收口替代）。

**集成前覆盖要求保持不变**：每个代码提交都必须落在真实 review ledger 审查范围内；此前未审的低风险代码在集成前补一次最小范围 review。已审范围没有后续代码变化时，不重复跑相同的全量 review。Review 修复提交也必须被后续 review 范围覆盖；代码提交不得用 whitelist 放行。

## 3. 完成与集成

1. 更新 Tracker、`PHASE_STATUS.md` 当前焦点 / 索引和当月归档；每条事实只写全一次，其余位置给指针。
2. 集成前按 `AGENTS.md` §14.10 通过全量测试、lint、type check（如有）、`git diff --check`、审查覆盖闸门及工作树检查；比较 tree，确认集成内容与已验证内容一致。**全量只跑一次的老家规矩见 §8.1**：跑在冻结树，读数按 §8.1 第 3 条的**两条判据**传递到被集成的代码面（判据原文、`--name-status` 要求与自证步骤见该条，此处不复述以免两处漂移）。
3. Branch merge、push、issue close 和跨仓库同步遵守 `AGENTS.md` §13–14。前一阶段的授权不自动扩大到下一种 Git 写操作；冲突按 §14.7 分析并取得批准。

### 3.1 不确定与票面变化

不要用猜测代替规格或用户决定。若验收条件不可实现、证据推翻原假设，或存在会改变架构 / 范围 / 数据迁移的选择，先停止相关实现，提交可复现证据、影响和最小替代方案，请用户批准后再改票面或计划。普通实现细节自行判断，不频繁打断用户。

### 3.2 Git 与推送

- 实现线默认只做本地 commit，不在 feature branch 上 push。
- 集成与 `push origin main` 的授权分类、前置条件和通知要求统一见 `AGENTS.md` §14.4、§14.9、§14.10；本文件不重复定义。

## 4. Context Window 恢复协议

任何新 context window 启动时，按以下顺序恢复：

0. **先执行上面的自愈条款**（不确定就重读，不猜）
1. 读 `docs/SDD_WORKFLOW_PROTOCOL.md`（本文件）

3. 核对 `git status`、分支与 HEAD；确认无用户改动被覆盖
4. 根据 Tracker 与当前用户授权继续工作

### 4.1 恢复时的自检清单

- [ ] 当前在哪个 worktree？（`git worktree list`）

- [ ] 哪些代码 commit 已有 review 覆盖，哪些尚待 review？（查 Tracker + `review_ledger.tsv`）
- [ ] 是否有未修完的 review finding 或待用户决定事项？

## 5. Ticket Tracker 与进度记录

`docs/SDD_TICKET_TRACKER.md` 记录每个 ticket 的状态：

| 字段 | 说明 |
| --- | --- |
| Ticket ID | 如 FE-T7 |
| 描述 | 一句话说明 |
| 状态 | 记录项目当前使用的 Ticket 状态；`batched` 等旧批次状态只保留为历史 |
| 实现方式 | 用了什么 skill、改了哪些文件 |
| Commit SHA | 完成时的 commit hash |
| 门禁结果 | 前端：tsc/vitest/oxlint/playwright/build；后端：ruff/pytest（+ 真机 gate/变异，若有） |

历史批次记录（V1/V2）：

| 字段 | 说明 |
| --- | --- |
| 批次号 | 如 `B1`、`B2` |
| 本批 tickets | 这批包含哪几个 ticket |
| fixed point | 本批累计 diff 的起点 commit（= 上一批审查结束时的 commit） |
| 审查结论 | 轮次 + findings 分级 + 是否零 finding |
| 修复 commit | 当时 findings 修完后的 commit；该字段保留历史事实，不定义 V3-lite 审查节奏 |

⚠ **表格里的范围数字只是人读的索引；交付前"哪些 commit 真的被审过"以机读台账
`docs/review_ledger.tsv` 为准**（覆盖对账见 §7 第 8 条——手抄的 review 范围错一格就是
#213 那次静默豁免）。审查行的 tip 必须 = **审查实际读到的末条 commit**：审查之后才创建的
修复提交**不在**那个范围内，必须由另一条真实 review 行覆盖。

## 7. 执行边界与集成闸门

1. **按风险安排 review**：不设固定 Ticket 数量节奏。集成前每个代码 commit 都必须有真实 review ledger 覆盖；审查范围缺口在集成前补齐。
2. **使用实际可用的 Skills / 命令**：按任务需要选择；不要求不存在的 `/implement`、`/ask-matt` 或其他工具。
3. **feature branch 不 push**：本地 commit 可以；push 与集成授权按 `AGENTS.md` §14.4 执行。
4. **规格外架构决策先问用户**：按 `AGENTS.md` §9.1 / §9.1.1 处理新证据、验收条件和范围变化。
5. **禁止跨仓库无授权写入**：`D:\intelligence-agent`（main）、`D:\intelligence-agent-backend`、
   `D:\intelligence-agent-frontend` 是**三个独立 clone**（不是 worktree），各有自己的工作树与分支。
   用户可以授权任意一条线做另一端的活，但**动手前必须先读 `AGENTS.md` §13 的仓库模型**——
   "三方一致"靠"谁集成谁通知、另一条线开工前先把 main 合回来"维持，不靠目录名分工。
6. **按改动选择逐票验证，集成前通过完整门禁**：逐票跑相关 focused tests、lint / type check 和必要的集成测试；不要求每张票都重跑全量。集成前完整门禁见 `AGENTS.md` §14.10：后端 `ruff check` + 全量 `pytest`；前端（在 `web/` 下）
   `npx tsc -b && npx vitest run && npx oxlint && npx playwright test --workers=2 && npx vite build`。
   e2e 必须 `--workers=2`（4 worker 全量并行存在资源竞争型抖动）。
   **后端测试当前的跑法（用户 2026-09-21 指令）**：`PYTHONUTF8=1 .venv/Scripts/python.exe -m pytest -q -p no:randomly`
   ——下方的 `uv run` 规则**只在确实使用了 `uv run` 时**适用（用没用，以实际命令为准）。
   若用了 `uv run`：它会在锁过期时**静默重写 `uv.lock`**。所以跑完先看
   `git status`：若出现 `uv.lock` 改动，说明提交的锁与 `pyproject.toml` 不同步（#216）。
   处置：**立刻以独立的 chore commit 落地**（`chore(#216): uv.lock 同步`）——不要用
   `git add -A` 把它混进功能票，也不要为了"工作树干净"顺手 `git checkout -- uv.lock`
   （那只是把不同步藏起来，下一次 `uv run` 还会再改一次）。§14.10 要求的"工作树 clean"
   指的是**进入集成之前**：这份改动同样要有归属的 commit，不能带着未提交的锁进集成。
7. **禁止凭记忆猜流程**：不确定就执行自愈条款（重读本文件 + Tracker）
8. **禁止未审查的代码 commit 进集成**：交付前跑 `scripts/check_review_coverage.py`（台账
   `docs/review_ledger.tsv` + `docs/review_ledger.d/*.tsv` 双读；`.sh` 冻结为语义参考，只对拆分前布局成立）。它机械地对账「`<最早台账 base>..HEAD` 的每条 commit 是否有
   台账归属」，**例外两类**：
   - `[whitelist]` 段的 **docs-only** commit（脚本自己校验：改动文件全部命中文档扩展名；
     `docs/` 下只认 .md/.txt/.rst/.tsv/.json/.yaml —— 仓库里就有 `docs/integration/*.sh`，
     按 `docs/` 前缀放行会把可执行脚本当散文，2026-09-17 两轴审查 P1 实测复现）；
   - **恰好只改台账文件本身**的记账提交（机械可验、藏不了代码，自动放行——"把记账这件事
     记进台账"再要求记账是**死循环**，实测绕了三轮）。

   **代码提交永远不能靠白名单放行，必须落在真实 review 行中**。为什么需要这条（2026-09-17 实测
   两个案例，都是复验才发现）：
   - **#213 从未被任何 review 读过**：旧 V2 把 fixed point 作为批次边界，
     但那个数字是**手抄进 tracker 的**，抄过一格（把 fixed point 设在该票自己的末条提交上）
     就静默豁免一票，没有任何东西会报错；
   - **修复提交结构性免疫**：旧 V2 表格写着「修复 commit = 下一批的 fixed point」，于是交付
     周期里**最后一次审查的修复提交没有下一批**。实测 `9f2a8f8` 就是这样进的 main，而补审它
     时发现它带着一个真 bug（凭据删除 fail-open）。

   **信任边界（如实写，别把它读成"审查真的发生过"）**：台账是**声明式输入**，审查行的真实性
   由人对账——脚本只能证明"每条 commit 都有归属"，不能证明审查内容真实或完整。三点已知限制：
   ① 审计窗口的**左端由台账自己决定**（删掉最早那行即可整体缩短窗口，脚本无外部锚点）；
   ② 台账从**工作树**读，不读 HEAD 版 ⇒ 必须在**干净检出**上跑；
   ③ 机器强制只在本 clone 成立：两侧仍无 CI；本 clone 已有本地 `pre-push` hook（Gate-0 含本闸门车道），但 `core.hooksPath` 是本地配置、不随仓库分发，且 `--no-verify` 可绕过（§8.3 第 7 条前提块）。
   新增 review 后：把准确范围写进台账新行，并更新 Tracker 的 review 状态与证据指针。**不要改台账蒙过去**。

   **门禁读数一律来自机器落盘（2026-09-22 新增，issue #293）；"人抄"这条路径本身已删除**：
   `scripts/gate0.py` 每次**裸全量**运行都把读数写成 `docs/gate/<head sha>.json` —— `sha` +
   `git rev-parse <sha>^{tree}` + 每车道结论 + 墙钟 + 工具版本；`--no-record` 关闭落盘；
   `--replay <file>` 在另一棵树上独立复核该文件（比对判定，**墙钟不参与**）。
   **落盘前要求工作树不偏离 `HEAD`**：车道跑在**工作树**上、读数只能记 `HEAD` 的树，两者不一致
   就等于把读数指到了一棵**没被测过的树**（§8.7 第 3 条）⇒ 拒绝落盘并 FAIL（fail-closed）。
   判据是**三条独立检查**，**不是**"看 `git status` 干不干净"：① 追踪文件的内容/类型偏离
   （显式带 `--untracked-files=all`，本地 config 挡不住）；② `assume-unchanged` / `skip-worktree`
   位 —— ⚠ 这两个位让 `git status` **完全失明**，必须单独查 `git ls-files -v`（2026-09-22 R1 的
   两轴**各自实测出可绕过**，旧判据正是这样漏的）；③ 未跟踪文件里**后缀命中车道输入**的那些 ——
   ⚠ `git status` 天生遵守 `.git/info/exclude` 且**没有任何 config 能关掉它**：把未跟踪的车道
   语义文件（`conftest.py` / `ruff.toml` / `tsconfig*.json` …）藏进去后 status 完全失明、车道在
   ≠HEAD 的被污染工作树上跑（2026-09-23 严格审查实测复现，P1-c 同族姐妹面）⇒ ③ 的枚举源是
   `status` ∪ `git ls-files --others --exclude-per-directory=.gitignore`（只应用**已入库**的
   `.gitignore`、绕开 `info/exclude` 与 `core.excludesFile` 两个本地藏匿面；裸 `--others` 会把
   node_modules 等 5 万+ 噪音灌进读数，本仓实测 55422 条），方向 fail-closed（本地藏不住、
   噪音不暴涨）。
   其余未跟踪文件只**如实记进读数的 `worktree.untracked`**、不据以拒绝（本仓稳态就有
   `?? .zcodeignore`；把它当拒绝理由会让"读数的唯一来源"永久卡死）。
   ⇒ 台账行 / Tracker / 月档 / 关单 comment / 落点记录里出现的**任何**门禁读数都必须**写路径**、
   **不抄数字**。为什么要把"人抄"整条路拿掉：#213 就是**手抄 fixed point 错一格**而静默豁免一票，
   **没有任何东西会报错**。缺文件（例如那棵树是在本机制落地前跑的）⇒ 现跑一次 Gate-0 生成，
   或按 §8.7 第 3 条当作"来源树不明的读数"作废重跑 —— **不要凭记忆补数字**。

   顺带（同一批实测得出）：**集成后不必重复跑全量门禁——先比 `HEAD^{tree}`**。两个 clone 的
   tree 相同即证明"跑过门禁的那棵树 = 被集成的这棵树"（2026-09-17 实测同为 `e63c202…`，
   省掉一次 ~20 分钟的 前后端全量）；不等才在集成 clone 里跑（细节见 `AGENTS.md` §13.4）。

## 8. V3.1 提速增补（2026-09-21，保守型：只砍浪费，不砍验证）

**总则（质量优先条款，本节最高优先）**：本节的每条规则都只在**不减少任何验证强度**时适用。
判断标准是三问：① 这条规则会不会让某个本该跑的验证**不跑**？② 会不会让某个读数**来源不明**
（不知道它跑在哪棵树上/哪个状态下）？③ 会不会让某个结论**没有责任人**（没人独立看、没人签字）？
任何一问答"会"⇒ 该条不适用，按 V3-lite 原样执行，并把冲突与代价记进 `docs/SDD_TICKET_TRACKER.md`。
"读起来更省事"不是适用理由。

### 8.1 冻结树单次全量（省：每批 2–3 次全量 → 1 次，约 20–30 分钟）

1. **冻结树**：本批不再打算改 `src/**` / `tests/**` / `web/**` / 配置 / `scripts/**` 的那棵树。
   冻结动作 = 记下 `git rev-parse <sha>`、`<sha>^{tree}`，以及被改动文件的 `git hash-object`（写进 Tracker 的门禁证据）。
2. **全量只在冻结树上跑一次**。冻结之前的中间树只跑 focused 子集（相关目录 / 相关文件）。
   "再改一点再全量一次"是明确要消灭的浪费。
3. **读数传递（机械可验，不允许口头推理）**：冻结之后若只追加 `docs/**` 与台账提交，
   用 **两条**判据证明"跑过门禁的树 = 被集成的代码面"：
   ① `git diff --name-status --no-renames <冻结sha> HEAD`：**状态列只允许 `A` / `M`**
   （出现 `D` / `R` / `C` / `T` ⇒ 一律重跑——删除与重命名会让"代码面未变"这个 claim 不成立），
   **且每条的路径都命中 docs-only 模式**（`DOC_PATTERN`，与 `scripts/check_review_coverage.sh:51` 同一个模式：
   `docs/**` 下只认 .md/.txt/.rst/.tsv/.json/.yaml，加根级 `AGENTS.md`/`CLAUDE.md`/`CONTEXT.md`/*.md）。
   ⚠ **必须用 `--name-status` 而不是 `--name-only`**：后者不带状态列，**删除与修改同形**
   （实测 2026-09-21：`git diff --name-only --no-renames a3afd18^ a3afd18` 把一个**删除**
   `docs/INTEGRATION_PROMPT_REVIEW_STRUCTURAL_FRONTEND.md` 显示成普通文件名，`grep -Evc` 得 **0** ⇒ 放行；
   换 `--name-status` 才看到 `D`）；
   ② 逐行看 `git status --short`：**每行路径都必须命中同一个 `DOC_PATTERN`**，唯一例外是 `?? .zcodeignore`
   （用户本机数据，永不提交）；出现任何其它未提交改动（含未跟踪文件、含 `docs/**.py` 这类"在 docs/ 下但不是文档扩展名"的路径）
   ⇒ 读数作废。判据 ① 只比两个 commit，**看不见工作树**，故 ② 不可省。
   这条判据必须比"只比 `src tests`"宽：本仓 `web/` 就在根上（§7 第 6 条把前端门禁算作完整门禁的一部分）、
   `pyproject.toml` 直接定义"全量收集什么"、`scripts/` 住着唯一的机械闸门——只比 `src tests` 时
   这些改动**一条都看不见**（实测：`git diff <sha> --stat -- src tests` 对一次真实的 `web/**` 改动输出为空，
   即会对过期读数放行）。**出现任何非 docs / 台账路径 ⇒ 必须在新树上重跑全量**，不允许"看起来只是小改"。
   **不许把本条读成 §13.4 的 tree 比较**（那条比的是整棵 `HEAD^{tree}`；本条是"文档面之外无改动"的等价条件，
   判据形式不同）。
   **例外（2026-09-23 新增，来源 = B-43 报告缺陷 1）：纯注释 / 纯 docstring 的 `src/**` diff 判「语义等价」，
   读数可传递、不重开冻结树。** 动机（实测）：`src/**/*.py` 不在 `DOC_PATTERN` 内 ⇒ 任何 `src/**` 改动（**哪怕只改一行
   注释**）都让判据 ① 不成立 ⇒ 须重跑全量 + §8.8.5 的修后重审 ⇒ 理性选择是**推迟修复**，已知缺陷随交付进 main
   （B-43 的实际结局：`provider.activate` 的 docstring 对 `max_depth=0` 描述夸大，两轴**各自独立**报出，因代价过高未就地修）。
   **判据（严格版，机械可验）**：
   1. 取改动前后两个 blob（`git rev-parse <冻结sha>:<path>` 与 `git rev-parse HEAD:<path>`），各自 `ast.parse`；
   2. 把 `docstring`（模块 / 类 / 函数三级）与全部注释**剥离**后归一化（`ast.unparse` 或 token 流序列化）；
   3. **归一化结果逐字节相同** ⇒ 判「语义等价 ⇒ 读数可传递」，本节判据 ①② 对该路径**免检**；
   4. **判据必须自证可证伪，且控制样本必须进测试（不只是写文档）**：至少要有一个**负控** ——
      「只在注释里改了字面量 / 默认值」的样本 ⇒ 判据必须判**不等价**（防止把注释当垃圾桶夹带真实改动）；
      一个**正控** —— 「只改 docstring 措辞」⇒ 判**等价**；另加**删真语句反控** —— 删掉一行真语句（哪怕只是 `pass`）
      ⇒ 判**不等价**（证明判据只对「删掉的都是 docstring/注释」成立）。三个控制样本都进测试。
      **判据的机器实现与这三个控制样本归属代码面票 `#295`**（`scripts/check_semantic_equiv.py`）：
      本条只写口径 —— 判据本身是代码，而 `docs/**/*.py` 不命中 `DOC_PATTERN`、`scripts/*.py` 属代码面，
      **本票（纯 docs）内没有任何放置可执行 `.py` 的合法落点**（实测 2026-09-23）。
   5. **判为不等价时的出路**：允许该 P3 修复**顺带进下一批**（不重开本批冻结树），但**台账必须写明**
      「未随本批修复 + 原因 + 归属下一批的票号」。
   **本条不修改判据 ① 对 `DOC_PATTERN` 的定义** —— 它是**并列新增**的例外，判据只增不减。
4. **判据必须先自证可执行**：跑判据前**逐个**验证两个对象——
   `git rev-parse --verify <冻结sha>^{commit} && git rev-parse --verify HEAD^{commit}`。
   **必须分次调用且带 `^{commit}`**：`git rev-parse --verify <a> <b>` 一次传两个参数**恒 exit 128**
   （`fatal: Needed a single revision`），与该命令"对象不存在"的报错**同形**（2026-09-21 实测）⇒
   自证本身会变成假绿；`scripts/check_review_coverage.sh:74-75` 用的是同一 fail-closed 形状（`--verify --quiet || exit 1`）。
   **照抄时先替换占位符**：模板里的 `<冻结sha>` 带 `<`，shell 会当**输入重定向**——实测
   `git rev-parse --verify <冻结sha>^{commit}` 报 `冻结sha: No such file or directory`、exit 1，整条命令
   根本没跑（也不留下杂散文件）；换成变量并整体加引号即成立：`git rev-parse --verify "$FROZEN^{commit}"`
   （实测 exit 0）。**裸写的 `^{commit}` 在 bash 下不是特殊字符**（`git rev-parse --verify 20ee173^{commit}`
   实测 exit 0）——加引号是为跨 shell 稳妥，不是 bash 的硬要求。2026-09-21 更正：本条首版把 `^{commit}`
   与占位符**并列**写成"重定向符"，属过度声明，已按实测改写。
   **stdout 为空 + exit≠0 不算通过**（`git diff <抄错的sha> HEAD` 恰好 stdout 空、exit 128 ⇒ 抄错一位就假绿，
   与 §7 第 8 条记的 #213 手抄事故同形状）。两条判据的**输出原文**写进 Tracker 门禁证据；
   **证据缺失等同于没跑**。
5. **并行**：全量可以在后台跑，同时写 docs / 台账 / 关单材料——但必须满足第 6 条的隔离条件。
6. **防污染：靠隔离，不靠快照**。全量运行期间，**主工作树禁止任何改动**（含变异脚本、审查者自写变异、
   手工编辑、切分支）。**造变异/红证必须在主工作树之外的副本里做**：把仓库复制/克隆到临时目录
   （`git clone --no-hardlinks . <临时目录>`，或复制 `src/` + `tests/` + `pyproject.toml` 后在副本里 `git init`）。
   **副本里跑测试必须显式设 `PYTHONPATH=<副本>/src`**（cwd = 副本），否则**读的还是主仓的 `src`**：
   本仓 `pyproject.toml:59` 的 `pythonpath = ["."]` 只加 rootdir（副本根），而 `src` 由
   `.venv/Lib/site-packages/intelligence_agent.pth` **里的一行绝对路径**提供（`D:\intelligence-agent-backend\src`）
   —— 于是出现"**副本的测试生效、副本的 `src` 静默无效**"这种混合解析（2026-09-21 实测：不带 `PYTHONPATH` 时
   cwd=副本、`agent_harness.__file__` 仍指主仓 `src`；往副本 `src` 里塞一个哨兵属性后，不带 `PYTHONPATH` 的探针
   断言**看不见该属性**、带上后才看见 ⇒ 变异在副本里可能"看起来完全没影响"，两边都会得出错误结论）。
   **副本操作前必须先探测行尾（2026-09-23 新增，来源 = B-43 报告缺陷 4）**：
   `git archive` 出来的副本**按仓库存储格式落盘**，而本仓 `core.autocrlf=true` ⇒ **副本里的 `src/**` 是 CRLF**
   （B-43 实测 `depth.py` 含 `b'\r\n'`）。若变异脚本用 `\n` 写多行锚点 ⇒ `str.replace()` **静默 0 命中**，
   产生「对照绿 / 变异也绿」的假读数，看起来像「用例没鉴别力」。**硬要求**：
   ① 操作副本前先探测行尾（`b"\r\n" in raw`），多行锚点**按探测结果归一**；
   ② **断言命中数 `== 1`**；`0` 命中 = 修改**没发生**（不是「没影响」）；
   ③ **无命中数断言的 `.replace()` 是危险形式**，一律不得使用。
   理由：本条的失败形态是**假绿**（看起来变异了、其实没有），与「用例无鉴别力」**同形**，
   不靠命中数断言无法区分二者。
   **做不到隔离 ⇒ 三路串行**（§8.2 的并行承诺作废，按 V3-lite 原样）。
   理由（两轴实测）：审查**子代理**会把变异留在工作树里，而"变异完再还原"恰好让**前后快照都干净**——
   §8.1 早期版本靠"前后 `git status` + `hash-object` 比对"判污染，**这种判据抓不到"改完又还原"**，
   于是采自变异树的全量读数会被当有效门禁。快照仍要记（能抓"忘了还原"），但**判据是"窗口内有没有发生变异"
   ——只能靠隔离保证，不能靠快照证明**；一旦发现主工作树在窗口内被改过，该次读数**作废重跑**。

### 8.2 冻结即三路并行（省：约 30–40 分钟的串行等待）

1. 代码面**冻结后立即**并行启动三件事，全部锚同一个冻结 sha：**两轴独立审查 ∥ 作者红证 ∥ 全量门禁**。
2. **作者的变异红证不是审查的前置**（此前串行做过，纯浪费）；审查者也**不需要**等全量跑完。
   **并行的前提是 §8.1 第 6 条的隔离**：造变异的一方（作者红证 / 审查者自写变异）在主工作树**之外**的副本里工作；
   做不到隔离 ⇒ 三件**串行**（先红证/审查，后全量）。
3. 守卫：三者中任何一个导致**主工作树**代码面变化 ⇒ 另外两个的读数作废，在新冻结树上重跑（只追加 docs / 台账
   的情况按 8.1 第 3 条的两条判据处理）。**不因为"已经花了很多时间"就沿用过期读数。**

### 8.3 审查预算、"修后重审"的有界收口与**新内容的补审**（省：约 30–60 分钟）

1. **派单必须给预算**，写在 prompt 里：目标 sha（含 `git hash-object` 期望值）、报告上限
   （结论行 + findings 列表 + 证据读数，**不贴大段源码**）、墙钟上限、自写变异条数上限，
   以及 **"无论跑到哪一步都必须给出结论行"**（可以写"预算内未见 P0/P1/P2"）。
2. **只读纪律 + 收尾自证**：允许为造变异临时改文件，但**只能在主工作树之外的副本里改**（§8.1 第 6 条，
   含 `PYTHONPATH=<副本>/src` 这一条）。**没有例外**：主工作树里**发生过**变异（哪怕已逐字节还原、
   哪怕审查者自报干净）⇒ 与它同窗口的全量读数**作废**——还原与自报只用于**恢复工作树**，
   **不能**用来证明读数有效（这正是 §8.1 第 6 条要堵的形状）。收尾仍要报 `git status --short` 与
   所改文件的 `git hash-object`（抓"忘了还原"），**编排侧在采信结论前必须验收工作树**
   （工作树恢复到预期 hash）——这是"审查可采信"的机械条件，不是礼节。
3. **发现阶段（初始两轴）不可替代**：两轴都必须给出结论；子代理基础设施故障可以重派（建议 ≤2 次），
   但**不允许**用"另一轴 + 作者红证"代替第二轴的**发现**结论。（**是否**需要独立审查按 §2 的风险分档判定；
   §2 的"低风险可并入最近自然边界"只影响**审不审**，**不构成单轴通道**——一旦审，发现阶段就是两轴。）
4. **修后重审**（**以闭合既有 findings 为主**，但**不得零发现**：修复提交是全新代码面，至少要有一次有限发现
   ——审查者自写变异或逐处红证覆盖，二者其一）每轴**预算 1 轮**。
   **「红证」与「变异」是两个术语，目的相反，不得互相顶替（2026-09-23 新增，来源 = B-43 报告缺陷 2）**：
   - **红证（red proof）**：在**改动前的树**上跑新用例 ⇒ 红；在**改动后的树**上跑 ⇒ 绿。
     它证明的是「**用例能发现实现缺失**」。
   - **变异（mutation）**：在**改动后的树**上**破坏实现** ⇒ 用例转红。
     它证明的是「**用例有鉴别力**（能区分正确实现与错误实现）」。
   - **实测反例（B-43）**：M1（`if allowance <= 0:` → `if False:`）与 M2（`child_allowance` 忽略
     `parent.remaining-1`）命中**完全相同**的三条用例 ⇒ 单看任一条都会误判「其余检查也被覆盖」。
     故要求：**变异至少覆盖两个不同检查点且失败集合不同**；若失败集合相同 ⇒ 必须登记
     「**共用失败面，互不构成鉴别力证据**」——不得据此宣称鉴别力已证。
   **无第二轮（2026-09-22 修订）**：该轮若在本轮修复**新引入的代码面**上再给出 P0/P1 ⇒ **停止修复**，
   如实登记轮数与残余，**交用户裁决**——不自动「再修 + 再窄复验」。原「**例外（不算超预算）**」条款已删除：
   它是「修后重审」被无上限展开的入口；实测把 B-35 拉到五轮、B-36 拉到四轮，末轮只改注释与措辞，纯墙钟开销（轮数当场复核：台账 B-35 段 106–111 行 = 两轴 → B 轴复跑 → 窄复验（三轮）→ 四轮证伪复验 → 五轮闭合复核；tracker「## B-36」状态行 = 「四轮独立审查 … 共 8 个独立只读子代理」）。
   同一轴因**基础设施故障**连续 2 次拿不到结论 ⇒ 允许**有界收口替代**：另一轴的修后重审结论 **+**
   作者红证（对每条 finding 的"修复前绿 → 修复后红"实测，逐条给出）**+** 明文登记
   "该轮结论由 X 承担、Y 轴未取到结论（原因）"。
   **"基础设施故障"的定义要收紧，且必须留证据物**：指**上游 / 编排侧中断，且该子代理未产出任何结论行**
   （`Upstream stream ended before terminal chunk`、进程被杀、编排侧超时），必须附**原始失败文本**（或日志路径）
   与时间戳；**不含**"审查者把预算用在探索上所以慢"——派单预算（§8.3 第 1 条）是派单方自己定的，且第 1 条已强制
   "无论跑到哪一步都必须给出结论行"，故**"派单预算用尽"不构成基础设施故障**，不得据以消掉一整轴。
5. **替代的边界**：① 只对"修后重审"成立，**不适用于发现阶段**；② 只对基础设施故障成立，
   凡"审查者还在跑/可能有问题"都不算；③ 替代必须在台账行、Tracker、关单 comment **三处如实写明**；
   ④ **禁止**把"未取到结论"写成"通过"，也禁止在文档里让读者误以为两轴都给过结论；
   ⑤ **每批最多替代 1 次**，且替代必须在 Tracker 登记一条「**待补审**」残余；**该轴补齐之前不得再使用第二次替代**
   （连续两批都替代 = 事实上取消了那一轴）。
6. 任何 findings（无论严重度）都不得因为"预算用尽"而不记录——预算限制的是**篇幅与探索深度**，
   不是**诚实**。
7. **工具已经管的事，审查不再报（2026-09-22 新增；来源为 Matt 原版 `/code-review` 明文
   "Skip anything tooling already enforces"）**：`ruff` / `oxlint` / `tsc` / `vitest` / `pytest` /
   生成物同步守卫**已经能报出**的问题（格式、未用变量、类型错、生成物漂移、已被覆盖的断言失败），
   审查两轴**不再重复记录**。审查只报工具看不见的东西：规格偏离、边界与权限、耦合与跨层、
   遗漏的需求、语义错误。理由：本仓 Standards 轴与 `ruff`/`oxlint`/`AGENTS.md` §9.6 存在重叠，
   重复报出来只会变成又一轮 findings 处置。
   **前提（缺此前提则本条不适用——一端不报、另一端也不报 = 开天窗）**：「**已经能报出**」以
   「该工具**配置到位**、**且在当前环境真的被执行过**」为准 —— 判据是「**环境内跑没跑过**」，

   后端 `ruff` **无任何配置文件**（`ruff.toml` / `.ruff.toml` / `[tool.ruff]` 全无），但**上游默认
   规则集本身已很宽** ✓（实测 `--isolated` 下一个 4 行探针即触发 `UP009`；`S110` / `BLE001` /
   `PLW1510` / `FURB188` / `PIE810` 均在默认集内）——**强度随 ruff 版本漂移**（`ruff>=0.16.3`
   无上界）：升级 ruff 后本车道突然变红属「规则集变了」，不是代码变差。**执行面**：两侧
   **仍然没有 CI**；**本 clone 已启用**本地 `pre-push` hook（`.githooks/pre-push` →
   `scripts/gate0.py`，6 条机械车道、实测 20–40s），但 `core.hooksPath` 是**本地配置、不随仓库
   分发**、且 `--no-verify` 可绕过 ⇒ **本条豁免只在「本 clone 经 Gate-0 真的跑过」的那些项上
   成立，不得跨环境传递**。⇒ 本条**逐项生效**：`ruff` / `oxlint` / `tsc` / `vitest` / `pytest`
   的「配置到位」均已成立；「被执行过」只在本 clone 经 Gate-0 的那几条车道上成立。未执行的项
   （任何「配置了却没人跑」的检查、别人的 clone、被 `--no-verify` 绕过的推送）两轴**仍须照报**。
   **Gate-0 的覆盖范围不得被放大**：它只覆盖**机械可判项**（空白/冲突标记、`ruff`、`oxlint`、
   `tsc`、生成物同步守卫、覆盖闸门）——下一条的禁令仍然完整适用。
   **禁止**以本条为由跳过两轴对**语义 / 规格 / 边界 / 权限**的实质审查：本条只豁免
   「工具已能机械报出」的重复项。
8. **没被任何一轴读过的新内容 ⇒ 按"发现阶段"补审，一票一次（2026-09-22 新增，闭合 #291 的条文缝隙）**：
   第 4 条管的是**对修复动作本身**的重审；但修复轮次可能顺带产出**在发现阶段（第 3 条）从未进入过
   任何一轴审查范围的新内容** —— 实测 #291：修复提交里新增了协议 §8.8.8 的整节条文，初始两轴与
   R2 任一轴都**没读过**它。这种情形此前没有明文出口：按第 4 条读算"超预算"，按第 3 条读又不属于
   "初始发现阶段"。现在明确：
   - 它**不是**第 4 条末段说的"修复**新引入的**代码面"（那条的停止条件**不适用**）；它构成一个
     **新的发现对象** ⇒ 按**发现阶段**的规格补审（第 3 条：两轴都必须给出结论），
     **不占用**"修后重审每轴 1 轮"的预算。
   - **一票只允许一次**：同一票内，"发现阶段补审"至多触发一次。第二次再出现没被任何一轴读过的
     内容 ⇒ 停止，如实登记轮数与残余，交用户裁决（与第 4 条末段同一个出口，不自动"再补审 + 再窄复验"）。
   判据是「**该内容是否曾被任一轴的审查范围覆盖过**」，**不是**"它出现在第几轮"。反例（**不算**
   新内容 ⇒ 仍走第 4 条）：对发现阶段已读过的东西做**语义等价的改写**（改名、拆函数、调顺序、
   加注释）—— 面没变，只是形状变了。

### 8.4 批次合并：2–3 张相邻子票一批（省：每批 3–4 笔记账提交的仪式成本）

1. 允许把 **2–3 张**相邻子票合成一批；上限 3 张，**跨 Phase 不合并**。
   "**跨端**"指同一批里同时出现 `src/**` 与 `web/**` 的改动（本仓 `web/` 与 `src/` 同处一个 clone）
   ——出现即拆批，不按"跨仓库"理解。
2. 合并省的是**记账与集成的仪式**（docs 落点、台账行、集成 push、§14.9 通知各一次），
   **不是验证**：每张票各自的红→绿 / 等价性证据、逐票 AC 对账、逐票残余登记**一条不少**；
   审查按**批 diff** 做两轴，findings 与 AC 归属到票，**且审查报告必须逐票给结论行**（每票一小节）。
   批 diff 变大时"批级结论"不足以支撑单票关单（§14.12 是按票关单的），故逐票结论是硬要求。
3. **保守红线**：**"行为零变化"的票不得与改动它判据覆盖面的票同批**。门槛写死成三件可执行的事：
   ① **判据面清单进 Tracker**：该票的等价性/ golden 判据文件路径，以及"它依赖哪些共享夹具 / 替身"一并列出
   （从"判据文件"到"它覆盖哪些代码"的映射**必须落纸**——否则"是否出现"取决于操作者当场划的集合，事后无法复核；
   传递依赖正是这类票的真实风险面：B-27/B-28 的共享替身 + `order` 时间线就是例子）；
   ② **判据文件 blob 未变**：`git rev-parse <tip>:<path>` 等于基线值；
   ③ **每张同批票提交后各跑一次判据文件并要求绿**（秒级、机械，能抓住改判据**含义**的传递依赖改动）
   ——比"人判断某个文件中没出现在 diff 里"强得多。**测量点必须写死**：在该票**自己的提交树**上跑，
   且测量时树里不含本批其他票的未提交改动 ⇒ 本批必须**逐票落 commit**（等价性票 A → B → C），
   压成一个 commit 或让三票改动同时在树里，读数就不属于任何单票、等于没测。
   两条命令统一用 **`<冻结sha> HEAD` 两个 commit 相比**（不含工作树；工作树另按 §8.1 第 3 条判据 ② 验），
   与 §8.1 的写法一致。宁可不合并，也不让"等价性"这个 claim 失去可验证性。
4. 一批**只做一次集成**（一次 push、一次通知）；批次内部各票的提交顺序不影响覆盖闸门
   （闸门按 commit 对账，不按批次）。

### 8.5 记账压缩（省：每批 20–30 分钟的文档手术；**不删任何字段**）

1. **台账行**（`docs/review_ledger.tsv`）：必须保留 **日期 / 票号或批次号 / range（base..tip）/
   fixed point / 两轴结论（或 8.3 的替代登记）/ P 计数 / 证据指针**；**整行**压到 **≤ 约 600 字符、硬上限 800**
   （量法：对刚写的那行取字符数——含 `date\tdesc\trange` 三列），超出的叙述进当月归档。理由：脚本只机读三列，
   散文是给人看的，而归档已经写全——重复叙述正是 `AGENTS.md` §16.1 要清理的债务。
   **适用范围**：该上限**只对新写的行生效，不回改已有行**（实测 2026-09-21：61 条审查行里 31 条超 600，
   最长 2693；作者同批 5 行里 3 行超）——追溯压缩是另一件需要单独授权的事，不属于本节的"提速"。
2. **`docs/PHASE_STATUS.md`**：**新写的**索引条目建议 ≤ 1500 字符、硬上限 2000（量法：该行字符数）；
   "最近条目"每批**一条**，不再在本文件重述逐轮细节（明细只在归档）。
   **已有超限条目只登记、不追溯重写**（实测 2026-09-21：B-28 那条 2873 字符 > 2000 —— 该条已记入 tracker B-29；
   它的明细在当月归档里本来就有，压缩它是另一笔需要单独决定的事，不在"提速"范围内）。
3. **归档**（`docs/phase_status/<年-月>.md`）：**唯一写全逐条明细的地方**（批次做了什么 / 审查轮次与
   findings / 红证条数与判定 / 门禁精确读数 / 残余 / 集成与关单）。压缩只能压前两处，**不得压归档**。
4. 指针纪律不变：机制叙述 → 本文件或 ADR；tracker / PHASE_STATUS 只写操作性事实 + 指针。

### 8.6 既有红与已知 flake 的处置（省：重复证明与无谓重跑；**不放行未知红**）

**全量读数的默认跑法（2026-09-23 新增，来源 = B-43 报告缺陷 3）**：全量一律走
`scripts/run_tests_clean.sh`（清空 `PYTHONPATH`）；走 shim 降为**例外且必须标注**。
动机（实测）：沙箱的 safe-delete shim（`PYTHONPATH` 注入的 `sitecustomize.py`）维护**跨测试累积删除配额**
（`threshold: 50, scope: turn`）；全量后期配额耗尽 ⇒ `SystemExit(1)`，表现为 `tests/evaluation/*`
**假红**（B-43 实测 `3124 / 3 failed`，三条全为该形状）。该现象既已登记（`docs/agents/verification.md` §5、
`verification.map.tsv:58`、`ADR-0038:18`），处置脚本也在仓库里，**但默认跑法仍走 shim** ⇒ 每批全量后
仍要人工归因一轮（纯浪费）。
**环境项与真实红的区分要机械化**：门的判定是「**环境项之外** 0 失败」——`docs/gate/<sha>.json` 应带
结构化环境项字段（如 `env_failures: [...]`），使读者不必靠人工比对判断某条红是不是环境造成。
**执行边界**：若该结构化字段需要改 `scripts/gate0.py`，则**必须移入代码面票**（本票纯 docs，不改脚本）；
协议此处只写口径与判据。

1. **既有红（pre-existing gate failure）证明的标准配方**：把被改文件换回 pristine blob
   （`git show <base>:<path>`）→ 复跑同一门禁 → 对比断言文本与计数 → 恢复自己的字节并报 sha256。
   该配方与读数**只做一次**，写进 Tracker 残余（日志路径作旁证）；**同批后续票引用即可**，
   不必逐票重跑证明——除非该票动了同一文件。
   **读数必须落进版本控制的文本**（Tracker / 归档里写清断言文本、计数、判定）；日志路径只作旁证——
   `.workbuddy/` 之类被 gitignore，另一条线（§14.9 合过来后）**读不到**，跨批传递的结论不能只靠它。
2. **既有红不阻断本票交付**，但三条同时成立：① 关单 comment 必须逐条写"哪条 AC 不成立 + 证据 +
   为什么判为既有"；② **不许**出现"XX 全绿"这类与事实不符的表述；③ 记一条**待用户裁决**
   （是否授权修既有缺陷）。**不得**把"未证明为既有"的失败当既有红——未知红 = 阻断，按 §3.1 报告。
3. **已知环境 flake 登记表**：登记在 `docs/SDD_TICKET_TRACKER.md` 的「已知环境 flake」一节，
   每条含：测试 node id + **失败签名 + 证据 + 一次独立确认 + 状态**。签名字段必须**机械可复核**，
   要写死到具体层面：**具体失败断言那一行 / 那段文本** + 与预算或超时相关的具体数字（例：断言
   `"before" in result.stdout` 且 stdout 空、`duration_ms` 超预算）——**同一用例里其他断言行失败一律阻断**
   （把真失败洗成 flake 的通道在这里，不在"跑 3 次"这一步）。**同一 hazard 的兄弟用例**要么一并登记、
   要么写明"仅登记此一个 + 理由"（例：同文件同 budget 的 detached 版尚未实测失败 ⇒ 未登记，一旦出现同签名失败
   先按阻断处理）。使用条目的**双重前提**：① 该条目的「独立确认」栏**已填写**且状态为**生效**；
   ② **唯一**失败命中签名、冻结树未变。满足后才允许用"同树单跑 3 次、≥2 次通过"作 flake 证据而**不必重跑全量**，
   且**这 3 次必须当场重新采集**（不许引用历史日志）；若当场 3/3 失败 ⇒ **该条目立即失效**，本次按真失败阻断。
   读数照实写（例：`1 failed(已知 flake: <node id>) → 同树单跑 2/3 通过 → 最终树 0 failed`）。
   签名不一致、或测试不在表内 ⇒ 一律阻断。**新增条目必须附证据 + 一次独立确认**，
   且新增本身要有 commit 归属；**独立确认必须在能复现该环境的前提下取得**（例：docker 类 flake 必须有
   daemon 在场的机器；本机取不到 ⇒ 保持"不生效"并记一条待办，别用"本机跑 3 次都 skipped"充数）。
4. **测试运行器**：后端当前按用户指令用
   `PYTHONUTF8=1 .venv/Scripts/python.exe -m pytest -q -p no:randomly` 跑；§7 第 6 条的 `uv run` / `uv.lock`
   规则**只在确实使用了 `uv run` 时**适用（该脚注已写进 §7 第 6 条，那里才是它的适用前提）。

### 8.7 明确不做的事（防止"提速"被读成"放松"）

- 不设"跳过某一轴"的任何通道；发现阶段永远两轴。
- 不设"沿用上一批读数"的通道；跨批不传递任何门禁读数（跨批只传递 8.6 第 1 条的**既有红结论**与
  8.6 第 3 条的 **flake 登记**，两者都必须有**落在版本控制文本里**的读数）。
- 不跨批传递**来源树不明**的读数：任何门禁读数必须能指到它跑在哪棵树上（sha + `^{tree}`）。
- 不靠"运行前后快照一致"代替**隔离**来证明全量读数采自干净树（8.1 第 6 条：抓不到"改完又还原"）。
- 不用自声明的"基础设施故障"消掉一整轴：必须附原始失败文本 / 日志路径，且"派单预算用尽"不算（8.3 第 4 条）。
- 不让代码提交走白名单；不让 docs-only 白名单收任何 `.py` / 脚本。
- 不因为提速而缩小审查的 base..tip 范围，也不把"审查者没看到"的 commit 写进审查行。
- 不为省时间而跳过 `scripts/check_review_coverage.py`（本机唯一可运行的机械闸门；`.sh` 冻结为语义参考）。

### 8.8 唯一主干与失败回退边界表（增量验证；**不砍任何验证**）

**要解决什么**：需求方 2026-09-22 定稿的要求是**增量验证**——失败时**不整条流水线从头跑**，
只重跑**受影响的验证**。没有边界的"增量"就是放松：省掉的到底是浪费还是验证，取决于当场划的集合。
所以本节的产物是一张**逐阶段写死**的边界表，而不是一句原则。

**实测依据（为什么值得做）**：B-35 一票墙钟 165 分钟里 **137 分钟（83%）**花在处置审查意见、
B-36 = 35/53 分钟（66%），两票 `docs` 新增 **0 行** ⇒ 慢的不是实现，是**回退与重跑的范围**没人界定。

#### 8.8.1 唯一主干（七阶段）

```
Grill → Spec → Tickets → Implement ├─ TDD（红→绿）
                                   ├─ Tests（本票 focused；冻结树上全量一次）
                                   └─ Matt 双轴 Code Review（发现阶段，§8.3 第 3 条）
      → Runtime Verification → Evidence Gate → Merge
```

- **Implement 的三个子步是同一阶段内的三条必做线，不是可选支路。**
- 本节是阶段名与主干拓扑的**唯一权威**；§9 只负责钉"到哪个阶段读哪个文件"。
- 本节**不新增阶段、不新增工具、不改任何既有规则**——它只把已经散落在 §7 第 6 条（逐票 focused /
  集成前全量）、§7 第 8 条（**集成后**不必重复跑全量门禁，先比 `HEAD^{tree}`）、§2 末段（已审范围无后续代码变化
  时**不重复跑相同的全量 review**）与 §8.1–§8.6 的要求，拼成一张可查的表。

#### 8.8.2 增量不变量 INV-1（读数复用的唯一合法前提）

> **INV-1**：一条门禁读数要被复用，必须同时满足
> ① 能指到它跑在哪棵树上（`sha` + `git rev-parse <sha>^{tree}`，§8.7 第 3 条）；
> ② 自该读数之后**代码面未变**——即只追加了 `docs/**` 与台账提交，按 §8.1 第 3 条的**两条判据**
> （`git diff --name-status --no-renames <冻结sha> HEAD` 逐条为 `A`/`M` 且命中 `DOC_PATTERN`；
> 工作树 `git status --short` 逐行命中同一模式）可证。
> **例外（2026-09-23 起）**：纯注释 / 纯 docstring 的 `src/**` diff，按 §8.1 第 3 条的
> 「语义等价」判据（`ast` 剥离 docstring 与注释后归一化逐字节相同）同样满足本条 ②——
> 判据定义见那一处，此处不复制。

**代码面一变（含任何修复提交）⇒ 该阶段及其下游的全部读数作废**，必须按 §8.8.3 重跑。
上游（Grill / Spec / Tickets）的产物是文档：修复**没有**改动 spec 与票面时，其结论可保留
——这就是"不整条重来"的**全部**依据。

**这也是"不越过 §8.7"的全部保证**：省掉的只有「上游已定稿的文档产物」与「同一冻结树内已经跑过、
且代码面未变的车道」，**没有任何一条验证**因为"上次跑过"而消失——代码面一变，下游整个重跑。

#### 8.8.3 失败回退边界表

每格的前提都是 **INV-1**（**失败本身已经改了代码面的行**——Review / Runtime Verification / Merge——不适用：那些行的"可以跳过"另受机械映射约束——**该映射已落地**，见 §8.8.9）；"环内可以跳过"一列**只在修复迭代环内**成立，
**不含集成前那一次完整门禁**（§8.8.4 第 1 行）。

#### 8.8.5 「针对新 diff 的 review」= 修后重审，不是又一轮发现

**定义**：**针对新 diff 的 review** 指对「上一轮审查 tip → 本轮修复 tip」这**一段**代码面
（即本次修复引入的 diff）做的**修后重审**。范围**不是**整票全 diff，也**不是**全仓。两件必做：

1. **闭合既有 findings**：逐条给出「修复前红 → 修复后绿」的实测；
2. **在新 diff 上做至少一次有限发现**（审查者自写变异，或逐处红证，二者其一）——修复提交是全新
   代码面，**不得零发现**（§8.3 第 4 条）。

**与 §8.3 的严格对齐（逐条）**：

- **轴数不变**：仍是两轴（Standards 与 Correctness / Spec）。本节**不**提供任何单轴通道（§8.7 第 1 条）。
- **预算 = 1 轮/轴**，**无第二轮**（§8.3 第 4 条）：该轮若在本轮修复**新引入的代码面**上再给出
  P0/P1 ⇒ **停止修复**，如实登记轮数与残余，**交用户裁决**。
  ⇒ **禁止**把"针对新 diff 的 review"读成"每修一次就再开一轮"的入口；**判定**：若除初始两轴之外
  该票已用满 1 轮修后重审，就**不再开第 3 轮**，改为登记残余 + 请用户裁决。
- **"发现阶段补审"不占这 1 轮**（§8.3 第 8 条，2026-09-22 新增）：修复轮次里**没被任何一轴读过
  的新内容**（区别于"修复**新引入的**代码面"）按**发现阶段**补审，两轴都必须给结论，且**一票只
  允许一次**。它**不**放宽上面那条上界：补审之后若在本轮修复新引入的代码面上再给出 P0/P1，同样
  走"停止修复 + 登记残余 + 交用户裁决"。⇒ 本节的"已用满 1 轮"**只数修后重审的轮次**，不数补审。
- **冻结的 `.sh` 参考实现在拆台账后只对旧布局成立**（2026-09-22 登记）：`docs/review_ledger.d/`
  迁移后 `.sh` 读不到任何审查行（它只认单文件）⇒ 「同 tip 同结论」的对照口径自本日起**只对拆分前**
  的布局成立；本机唯一跑得动、也是唯一权威的实现是 `.py`（`.sh` 依赖 coreutils，本机默认 PATH 下跑不动——见 `AGENTS.md` §14.10 与审计包 §5.1）。**处置（2026-09-23 用户裁决：`.sh` 文件留作参考、一字不动）**：
  `AGENTS.md` §13.4 / §14.10 两处「同口径参考」的失真措辞已改准确（冻结语义参考、唯一可运行权威
  是 `.py`）；审计包 §9.4 实测**并无**「同口径」字样（其表述为「语义参考、冻结 / 参考实现（很慢）」，
  对照结论是在拆分前布局上的实测），作为历史档案不动。
- **它不是发现阶段**：初始两轴不可替代（§8.3 第 3 条）。「针对新 diff 的 review」只在"初始两轴已给过
  结论、且已有 findings 被修复"之后才存在；**不得**用它代替初始两轴。
- **台账必须写真范围**（§8.7 第 7 条）：审查行写 `<上一轮 tip>..<本轮 tip>`，**不得**写成"覆盖整票"，
  也不得把审查者没看到的 commit 写进去。

#### 8.8.9 受影响面的机器化（issue #292 落地：映射 · 守卫 · `--affected` · 维护环）

**三件套**（都在仓库内，按路径读即可）：

- `docs/agents/verification.map.tsv` —— 「代码面 ↔ 必跑车道 / focused 用例」的机械映射（24 行 × 8 列）。
  **四要素由五列承载**（`Driving it with <harness>` 拆成 `lanes` + `focused`），逐一对齐
  `docs/agents/skills/create-verification-skill` §3 的 feature 四要素：
  `Sub-features` → `sub_features`、`How to get to it (user POV)` → `how_to_get_to_it`、
  `Driving it with <harness>` → `lanes` + `focused`（「驱动它」的两半：跑哪些车道、跑哪些用例）、
  `Gotchas` → `gotchas`；另加三个**机械列**：`surface`（`--affected` 的匹配键，只允许**路径前缀**或
  **精确路径**，禁通配、禁 catch-all）、`layer`、`neg_tier`（`blast-radius` 阶梯）。
  `how_to_get_to_it` 是**散文**、`--affected` **不消费它**（它服务的是「人工逐行复核」）。**每一行都要承重**。
- `tests/test_verification_map.py` —— 守卫（**20 例**；编号与 `docs/agents/verification.md` §2 ⑭ **同源**，
  改一处必须两处同改）。① `git ls-files` 里**每个**被跟踪文件都被映射；② 结构合法
  （**8 列** / layer 唯一 / 车道 id 在词表内 / focused 路径存在 / `neg_tier ∈ 1..5`）；
  ③ **每一行都承重**（删掉任一行 ⇒ 至少一个文件的受影响集合发生变化）；④ **`focused` 必须真跑得动**——
  pytest 目标要对盘核到 `test_*.py`（`pytest <空目录>` 退出码 5，与 vitest 的 `No test files found`
  同形状，都是**假 FAIL**），且"哪些 focused 按设计不内联"要在守卫里**逐个登记**（见边界 5）；
  ⑤ **每一行都必须列无条件车道** `diff-check` + `coverage`（`verification.md` §1 决策表第 1 行「任何文件」）
  —— 漏列会让 `--affected` 在那个面上把它们**静默跳过**，那不是增量而是放松。
  该不变量**同时**落在 `scripts/gate0.py::parse_map` 的**解析期**：打开 map 就报错，不必等
  `--affected` 命中该面（2026-09-22 变异实测：摘掉某行的 `coverage` ⇒ 当场 `ValueError`）；
  ⑥ `how_to_get_to_it` 的形状**可机械判定**（要么写明「无用户入口」，要么引一个真实存在的仓库路径）；
  ⑦ 自带**独立**匹配器与**独立**求值器，对**每个**文件与 `gate0.py` 的求值**逐项相同**
  （map 与 `--affected` 不是两套真相）。它跑在 Gate-0 的 `guards` 车道里 ⇒ **映射腐烂 = 推送前就红**。
- `python scripts/gate0.py --affected <rev>` —— 消费映射：由 `<rev>..HEAD`（`<rev>` 亦可写成范围 `A..B`）
  的改动面算出受影响集合，只跑集合内的车道 + 受影响 focused 用例（**只内联 pytest 子集**，见边界 5）。
  **默认行为不变**（不带它恒跑全部 6 车道）。

**五条边界**（与 `docs/agents/verification.md` §4 **同源**，任一处改动必须两处同改）：

1. `--affected` **只**用于**失败后的增量重跑**；**不得**替代**推送前全量 Gate-0**（`.githooks/pre-push`
   恒不带它），也**不得**替代**集成前完整门禁**（§8.8.4 第 1 行）。
2. 改动面里出现**未映射路径** ⇒ **fail-closed**：退回全量并打印路径（核对不了就不放行）。
   同理**改动面为空**（如 `--affected HEAD`）⇒ **同样 fail-closed、不收敛成 0 条**：否则会打印出
   `Gate-0 PASS：0/0 通过`——一个与真 PASS **不可区分**的绿（2026-09-22 修后重审实测）。
   同时给了 `--since` 与 `--affected` ⇒ **一律以 `--affected` 的范围为准**（并先印说明），
   避免同一次输出里出现两个范围。
3. `neg_tier < 4` 的行必须被标成 **unproven**（`--affected` 会打印）：**依据 unproven 主张跳过任一条车道**，
   都必须在台账 / 落点记录里写明这一步是 unproven。**map 覆盖不到的读数一律重跑**。
4. 映射**不改变** §8.8.4 的清单：集成前完整门禁、两轴发现阶段、「针对新 diff 的 review」两件必做、
   覆盖闸门、造红隔离、读数能指到树、Runtime Verification 这个阶段本身 —— **一律照旧**。
5. **`focused` 的内联范围**（2026-09-22 定，两条血证）：`--affected` **只内联 pytest 子集**（`tests/**`
   或 `*.py`）；前端 / 浏览器类（`vitest` / `e2e` / `live`）与整个 `tests/`（= `pytest-full` **本身**，
   子集才便宜）一律**只登记、不内联**，逐条注明原因。血证 ①（坐标系混用）：`focused` 路径一律相对仓库根，
   而 vitest 的 cwd 是 `web/` ⇒ 把 `web/src` 原样当 filter 会 `No test files found, exiting with code 1`，
   是**假 FAIL**（那次改动根本没碰 `web/`）。血证 ②（潮水线以下的红）：**同一类干净树跑两次结果不同**
   ——一次 67 文件 1067 例中 1 例超时（B-29 已知 flake），一次 **67 文件 1067 例全绿**（20.0s）
   ⇒ 红是**非确定性**的（不是"恒红"），前端红**结构上无法归因**到本次改动。
   要让某个面内联，必须**同时**改 `scripts/gate0.py::focused_runner` 与守卫里的登记表——
   那是一道**要求明确表态**的锁，不是可以绕过的装饰。

**维护环（谁、什么时候）**：上游 `docs/agents/skills/maintain-verification-skill/SKILL.md` 给的是**方法**，
本节定的是本仓的**触发点**：

- **机械环（每次推送）**：Gate-0 的 `guards` 车道跑守卫测试。新增顶层代码面而不补映射 ⇒ 红。
- **落点环（每票落点时）**：该票改动面若落在某个 `surface` 上，落点记录里确认该行的 `lanes` / `focused` /
  `neg_tier` 仍然成立；不成立就改 map（**只改 map**；产品代码的真回归登记不修）。
- **完整环（维护波次）**：**每月一次**，或**出现跨模块大改批之后**（先到者为准），由**承担集成 AI** 发起，
  按上游方法跑「源波次 ∥ live 波次」，产出**一个 PR 的已证更正**。环内**只**允许改
  `verification.map.tsv` / `tests/test_verification_map.py` / `docs/agents/verification.md`；
  **禁止改产品代码**（漂移 ⇒ 改文档；真回归 ⇒ 报给人）—— 与 Scope Lock 同向。
