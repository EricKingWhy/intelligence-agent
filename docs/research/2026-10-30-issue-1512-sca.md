# Issue 1512: dependency scanning design basis

Decision date: 2026-10-30. Baseline: 2b04fa767137b2723f01a2a1f6a43ce7bd2cd2da.

## Sources and decision

- [pip-audit documentation](https://github.com/pypa/pip-audit): REUSE its vulnerability service and JSON reports for fully pinned requirements using `--no-deps --disable-pip`. It reports dependency advisories and aliases without installing the audited application; an exit status of 1 can indicate findings and must be interpreted with the report. It fits Python lock exports and the installer wheel closure. No upstream source is copied.
- [uv project export documentation](https://docs.astral.sh/uv/concepts/projects/export/): REUSE `uv export --locked` to produce pinned requirements from the committed lock, retaining environment markers. Production and all-extras/development are separate views; platform and interpreter markers limit the scan to the execution environment. No upstream source is copied.
- [pnpm audit documentation](https://pnpm.io/cli/audit): REUSE the registry-backed JSON audit for the committed pnpm lock, separately identifying production and development dependency views. Findings cause a nonzero exit; registry failures must not be silently treated as clean scans. No upstream source is copied.

The first two sources describe independent projects and mechanisms; the third covers the JavaScript ecosystem. Source links were inspected on 2026-10-30. No source code is ported; tool licenses remain with their respective distributions. The scan is evidence of reported advisories, not proof of exploitability or absence of vulnerabilities. The separately pinned Windows installer closure is included because it is actually shipped.
