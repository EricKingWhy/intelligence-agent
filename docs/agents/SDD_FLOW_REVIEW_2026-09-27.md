# SDD V3.1-lite 开发流程审查与提速方案

> 日期：2026-09-27 · 审查人：小深（WorkBuddy 线）
> 口径：本文所有数字均取自仓库实测（git log / `docs/SDD_TICKET_TRACKER.md` / `docs/phase_status/2026-09.md` / `docs/agents/SDD_ACCELERATION_AUDIT.md` / `docs/agents/SDD_V31_LIVE_VALIDATION_286.md` / `docs/gate/*.json`），估计值一律显式标注「估」。

## 0. 结论先行

1. **慢的主因不是实现，是审查轮次 + 流程仪式 + 集成尾部串行**。最硬的证据：B-35 墙钟 165 分里 137 分（83%）在处置审查意见；T8 的 157 分钟里，**审查两轮之外**的仪式与尾部占 88 分（56%）。
2. **粒度方差是最大的墙钟放大器**：大票 T7（37 文件、前后端同票）六轮审查、日历 9.8h；中票 T8 两轮审查、2.6h；极小票 #342 仅 7 分钟。「平均 3–4h」是被大票拉高的混合值。
3. **V3.1 已生效的提速条款是真的省**（冻结树单次全量、三路并行、无第二轮、记账压缩），#286 验证样本两轴各 1 轮收口。当前残余的慢，集中在 **7 个还没被机制覆盖的缝**（§3）。
4. 给出 **8 项优化**（§4），全部不动两轴 Matt code-review、不砍任何验证强度；按优先级落地后，**中位票预计 3–4h → 2–2.5h（估），大票（>6h）从流程上消失**。其中 2 项触及授权面 / 覆盖闸门语义，**需用户裁决**（§4 已逐条标注）。

## 2. 完整链路梳理（ticket → 交付，标注耗时 / 等待 / 返工）

```
Grill → Spec → Tickets → Implement(TDD/Tests) → [冻结] → 两轴审查 ∥ 红证 ∥ 全量
      → (修后重审 ≤1 轮/轴) → Runtime Verification(Live Gate) → Evidence Gate
      → 记账落点 → push(批准) → PR(批准) → CI gate0 → merge → 落账+读数落盘 → 关单
```

| 阶段 | 实测耗时 | 等待 | 返工（实测次数） |
| --- | --- | --- | --- |
| Grill / Spec / Tickets | 未单独计量 | 决策票停等用户拍板（有意设计） | #302 reranker 方向级返工 1 次（加后又 revert） |
| Implement / TDD | 随票变（不计入本文口径，见下注） | — | T7 实现 commit 后被 Live Gate 抓回 2 次（判据侧） |
| 两轴审查发现轮 | 33–38 min/轮 | 与红证/全量已并行（§8.2） | T7 六轮；B-35 五轮；B-36 四轮 |
| 机械面（ruff/tsc 全仓） | Gate-0 内 10–37s | **介入太晚**：审查轮后才抓回 27+1 条 ⇒ 定向两轴加开一轮 | T7 实测 1 次 |
| Live Gate（真模型） | 数 min × 次数 | 人工看读数 | T7 跑 4 次（2 次判据 bug 被拒 + 2 次重跑） |
| 全量 pytest | 11 min/冻结树 | 可与 docs 并行（§8.1-5） | shim 假红每批归因 1 轮 |
| 记账落点 | 2–5 笔/票 | 结构性强制 2 笔 + gate JSON 每 tip 一笔 | 每笔都走构造→提交→门禁 |
| 集成尾部 | **48 min（T8 实测）** | push/PR **各需单独批准**（截图实证）；CI 26s 串行等 | 「本地绿 CI 红」往返 2 次 |

> **口径注**：T8 的 157 min 从 feat commit（03:15）起算，实现本身的墙钟在 commit 之前、无落盘读数，本文不估。下文所有优化均指向**可计量的流程段**，不碰实现段。

## 3. 瓶颈根因（7 条，按证据强度排序）

### R1. 审查轮次是单票墙钟最大构成（证据最强）
B-35 83% / B-36 66% / T7 六轮。V3.1 已消灭「无上限重审」（#286 一轮收口），但**大票仍然多轮**——T7 的「定向两轴」就是权威车道在审查后才抓回缺陷触发的。**药在减少轮次的触发源，不在压缩审查本身**（两轴是用户硬约束，不动）。

### R2. 权威机械车道介入太晚 ⇒ 白送一轮定向审查
各审查轮里 ruff 只跑在改动文件上，而权威车道（gate0 全仓 `ruff check .` / `tsc -b`）在冻结/push 前才跑 ⇒ T7 被补抓 27 条 ruff + 1 条 tsc 真缺陷，**多开一轮定向两轴（~35 min）**。Matt 原版 "Skip anything tooling already enforces"（§8.3-7）的前提是「被执行过」——**执行时点从 push 前提前到派单前，机械面 findings 在源头上就不产生**。

### R3. 流程产物结构性多笔，commits 流被稀释 2/3
记账笔 > 交付笔（#286：3 vs 5）；「落点多文件 + 白名单恰好一台账文件」是协议强制的 2 笔结构；`docs/gate/<sha>.json` 每 tip 一文件再加 1–2 笔；Live Gate 证据入库每笔一次。每笔都要构造 → 提交 → 门禁 → 推送。

### R4. 环境不一致 ⇒ 结构性往返
- ruff EXE001 只在 Unix 生效，Windows 本地不可见 ⇒「本地绿推不出 CI 绿」已 2 次，每次 = 推分支→CI 红→修→再推（10–20 min + 上下文切换）。
- 沙箱 safe-delete shim 配额 ⇒ 每次全量 3 条 `tests/evaluation/*` 假红，归因对照已机械化（12s）但**没结构化进读数**，`3 failed` 每批都要文字抵消。

### R5. ticket 粒度无红线，跨端大票是超时主来源
T7 = 37 文件、src+web 同票 ⇒ 六轮审查、9.8h；§8.4 禁跨端「合批」但对「单票本身跨端」无约束；单票 diff 预算无判据。粒度方差直接解释「3–4h 平均」的分布尾巴。

### R6. 需求/验收标准前置不足 ⇒ 方向级返工
#302 reranker「加了又 revert（no quality gain）」：提升类需求没有量化验收阈值与最小实验设计，先做了再量、量了再退。

### R7. 上下文恢复成本单调增长 + 批准点串行
tracker 935KB（5 天翻倍）每次新 context 必读；push / PR / merge 各需单独批准（截图实证），多票并行时批准成为串行瓶颈。**§9.1.1 决策票停等是有意设计，不取消；但标准动作可以批量授权。**

> **模型能力 × 任务复杂度匹配度**：大票（37 文件跨端）超出单子代理审查预算与上下文（§8.3 派单预算含报告/变异条数上限——票越大，预算越容易耗在探索上）；tracker 体量吃上下文 ⇒ 断片恢复更频繁。⇒ R5（拆票）与 R7（瘦身）同时缓解「能力-复杂度错配」，不需要换模型。

## 4. 优化清单（按优先级）

> 每条含：改动内容 / 预期提速 / 实施成本 / 质量风险 / 依据。与业界做法的对应（小粒度拆分 / 并行 / 上下文模板化 / 自动化校验 / 前置验收）逐条标注。
> 已自查用户已否决清单（HANDOFF R3-1~R3-7）：**本清单无一命中**（不压 §9.5/§9.6、不并章节、不指针化 CLAUDE.md、不动跨仓副本、不改 Matt code-review）。

### P0-1 派审查单前，先固定跑一次 Gate-0 裸全量（≈60s）清零机械面 【自动化校验前置】
- **改动**：协议 §8.2 加一句：两轴派单**之前**先跑 `python scripts/gate0.py`（60s 内），机械面红 ⇒ 先修再派单；绿 ⇒ 两轴按 §8.3-7 天然豁免机械项。
- **预期提速**：大票省一整轮定向审查 ≈30–40 min；中小票省机械 findings 处置 ≈10–15 min。**这是「减少轮次」的药**（对照审计纪律：不是压字符）。
- **实施成本**：低——gate0.py 已在仓库，协议一句话（docs 两 commit 流程）。
- **质量风险**：无。机械检查**提前**做，审查强度不变，反而让两轴聚焦语义/规格/边界。
- **依据**：T7 的 27 条 ruff + 1 条 tsc 真缺陷全是审查后被权威车道抓回（tracker `## T7`）；§8.3-7 的豁免前提即「被执行过」。

### P0-2 本地门禁补齐「Unix-only 规则」等价检查 【自动化校验补盲】
- **改动**：gate0.py 加一条秒级车道：`scripts/*.py` 的 shebang ⇔ git index 可执行位一致性（纯 python 实现，不依赖 ruff 的平台行为）。
- **预期提速**：每次「本地绿 CI 红」事故省 10–20 min + 上下文切换；已实测发生 2 次。
- **实施成本**：低-中（代码面票：改动 + 测试 + 两轴审查）。
- **质量风险**：无（只加机械车道，fail-closed 方向）。
- **依据**：归档 L1349（EXE001 往返 ×2，`99a744fe` 曾补 7 个脚本可执行位）。

### P0-3 ticket 粒度红线：单票 diff 预算 + 跨端票默认拆 【小粒度任务拆分】
- **改动**：Tickets 阶段 checklist 加可执行判据——单票预算 **≤15 文件 且 净增 ≤~2000 行**；同票同时触碰 `src/**` 与 `web/**` ⇒ 默认拆成「后端票 → 前端投影票」串联；超预算必须票面写明理由。
- **预期提速**：大票消失 ⇒ 平均墙钟 3–4h → 2–2.5h（估，由 T7→T8 的规模-墙钟关系外推）；审查轮次同步下降（审查面小 ⇒ findings 少 ⇒ 轮次少）。**同时缓解模型能力错配**（R7 注）。
- **实施成本**：低（拆分纪律 + checklist；#317–#320 等后续票直接受益）。
- **质量风险**：票变多 ⇒ 记账/集成仪式次数变多——**必须与 P1-1 配套**，否则仪式成本抵消收益（这是本清单内最重要的一对联动）。
- **依据**：T7（大）9.8h 六轮 vs T8（中）2.6h 两轮 vs #342（极小）7min；§8.4 已有跨端不「合批」的同向先例。

### P1-1 记账结构合并：消掉「结构性 2 笔」+ gate JSON 每 tip 一文件 【上下文/记账模板化】
- **改动**：① `docs/gate/<sha>.json` 改固定名 `latest.json`（sha 在文件内容里，历史由 git 承载），或结论行直接进 tracker；② 允许「落点（docs-only 多文件）+ 白名单行」合并一笔（白名单引用**同批更早**提交即可自洽）。
- **预期提速**：每票省 2–3 笔记账提交 ≈15–25 min。
- **实施成本**：中——要同步改 `check_review_coverage.py` 的归属判定（代码面票）+ 协议 §7-8/§8.5（docs 票）。
- **质量风险**：**中——动覆盖闸门 = 动信任边界**。约束：fail-closed 语义一字不能弱；改动本身走两轴审查；⚠ 审计包 §9.4.1 已登记「白名单段去留」为**用户裁决项** ⇒ 本条须用户拍板后施工。
- **依据**：V3.1 验证报告 缺陷 5（交付 3 笔 vs 记账 5 笔）；T8 10/13 笔 docs。

### P1-2 Live Gate 判据自检前置：真模型之前先用 fake/静态校验过判据 【自动化校验前置】
- **改动**：Live Gate 场景判据（读哪个投影键、断言形状）在派真模型前，用 fake 模型或静态校验跑一遍「判据自检」；自检红 ⇒ 先修判据，不烧真模型往返。
- **预期提速**：每票省 1–2 次真模型往返 ≈10–30 min。
- **实施成本**：低-中（live_gate runner 加自检模式）。
- **质量风险**：低——自检是**前置**，不替代最终真跑（§8.8.4-7 Runtime Verification 这个阶段本身不动）。
- **依据**：T7 两次被拒全是判据侧 bug（`0285418` 读错投影键 TypeError、`509a229` 判据写法），不是产品 bug。

### P1-3 集成尾部并行化 + 「标准集成动作包」一次性授权 【并行处理 / 批量授权】
- **改动**：① 落账/归档/PHASE_STATUS **草稿**与服务端 CI 并行写（CI 绿之前不提交落账笔，顺序约束保留）；② 向用户申请标准包授权：「push 分支 + 开 PR + CI 绿后 merge」一次批准覆盖三步。
- **预期提速**：每票 ≈15–30 min（T8 尾部 48 min 中，CI 等待与批准等待约一半）。
- **实施成本**：低。
- **质量风险**：① 无（落账笔仍等 CI 绿）；② **授权面扩大 ⇒ 用户裁决项**——建议限定为「票面 AC 全绿 + 无残余裁决项」的票才适用标准包。
- **依据**：T8 尾部 48 min 实测分解；截图「推集成分支 + 开 PR（各需单独批准）」。

### P2-1 环境假红结构化进读数（`env_failures` 字段） 【自动化校验】
- **改动**：`docs/gate/<sha>.json` 增加结构化 `env_failures`（已知 shim/环境签名清单由 flake 登记表机读供给），门禁判定 = 「环境项之外 0 失败」，不再靠人工比对。
- **预期提速**：每次全量省一轮人工归因 ≈5–10 min；消灭「3 failed 天然是红灯」的解释成本。
- **实施成本**：中（改 gate0.py，代码面票）。注：缺陷 3 已登记此方向，`run_tests_clean.sh` 默认跑法已落地，本条是收尾的机械化。
- **质量风险**：低——环境签名必须来自登记表（双重前提已写死在 §8.6-3），不得现场新增。
